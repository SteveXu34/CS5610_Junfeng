# Acme Corp Website Reproduction
## Project Overview
This project is a reproduction of the Acme Corp demo website using only plain HTML, CSS, and JavaScript.
No frontend framework or Tailwind CSS is used in this project.
The goal was to reproduce the layout, navigation, content, and main interactions of the original website while keeping the implementation simple and understandable.

### Home

The Home page contains:
- A shared navigation bar with the Acme Corp logo
- Links to Products, Case Studies, Blog, About, and Contact
- A main heading:
  "Solutions for Every Impossible Problem"
- A short introduction paragraph
- A shared footer


### Products

The Products page displays a list of Acme products.
The product information is stored in JavaScript data and rendered dynamically instead of writing repeated HTML for every product.
The current products include:

### Case Studies

The Case Studies page contains two case studies:

## Changes and Adaptations

Some parts of the original website depend on external services that cannot be reproduced with a static HTML, CSS, and JavaScript project.

I made the following adaptations:
- Recreated the HubSpot contact form as a static HTML form
- Added a local success page for contact form submission
- Added a placeholder page for the HubSpot external link
- Added a placeholder Studio page for the Sanity CMS link
- Simulated gated case study access on the frontend
- Stored repeated Products, Case Studies, Team Members, and Navigation data in JavaScript
- Stored images, favicon, and the Geist font locally

These changes prevent users from reaching broken links while still representing the behavior of the original website.


## Data-Driven Content

Repeated content is stored in `js/data.js`.
Examples include:
- Navigation items (`navItems`)
- Products (`products`)
- Case studies (`caseStudies`)
- Team members (`teamMembers`)

JavaScript in `js/main.js` loops through the data and generates the corresponding HTML elements.
For example, the navigation bar is generated from one shared `navItems` array instead of manually rewriting the navigation markup on every page.
This means that if a new navigation item is added, the navigation data only needs to be updated in one place.


## Shared Navigation

Each page contains only an empty nav placeholder in its markup:

```html
<nav id="main-nav"></nav>
```

`js/main.js` finds that element, injects the Acme Corp logo, and then builds the
menu by looping over the `navItems` array in `js/data.js`. Because every page
loads the same two scripts, the navigation is defined in exactly one place. To
add or rename a link, I only edit `navItems` — no page markup changes are needed.

### Path convention (root-relative)

`index.html` sits at the project root (depth 0) while every other page sits one
level deep (`products/`, `about/`, …, depth 1). The same generated nav markup is
injected into pages at **both depths**, so a relative path like
`../products/products.html` cannot work everywhere — it only resolves correctly
from the subfolders, not from the root `index.html`.

To make one shared string work from any depth, the paths that are generated by
the shared scripts are **root-relative** (they start with `/`):

- `js/main.js` — logo link `/` and logo image `/Material/acme-logo.svg`
- `js/data.js` — every `navItems` link (`/products/products.html`, …) and every
  team member `image` (`/Material/...`)

Root-relative paths are resolved against the site's web root, so they behave
identically from the root page and from any subfolder page, both on Vercel and on
a local server. In-page links that never change depth (e.g. the case-study detail
links `first_one.html` / `second_one.html`, and each page's own
`<link>`/`<script>` tags) stay plain relative. The one trade-off is that the site
must be *served* rather than double-clicked — see **How to Demo** below.

## How to Demo

### Run it locally

Steps to run it:
1. Open a terminal in the project root:
   ```
   cd Hw2_Junfeng_CS5610
   ```
2. Start a local server (leave this window running — it stays busy on purpose):
   ```
   python3 -m http.server 8000
   ```
   You should see `Serving HTTP on ... port 8000`.
3. Open **http://localhost:8000/** in a browser — this loads `index.html`.
   Edit a file and just refresh the page; no need to restart the server.
4. When finished, press `Control + C` in the terminal to stop the server.
   (If port 8000 is busy, use another number like `8080` and match it in the URL.)

On Vercel none of this applies — the deployment is served from the project root
over `https://`, so the root-relative paths resolve automatically and
`index.html` is the default entry point.


### Empty / edge states
Accroding to the assignment requirement:
- **Blog** — there are no posts, so the page intentionally shows the empty-state
  message "No posts yet. Add one in the Studio," matching the real site. The
  Studio link goes to a local placeholder instead of a real CMS.
- **Products / Case Studies / About** — these are rendered by looping over their
  arrays. If an array in `js/data.js` were emptied, the loop simply runs zero
  times and the corresponding list renders empty rather than breaking.
- **Placeholder links** — the HubSpot branding link and the Studio link point to
  local placeholder pages so nothing in the demo leads to a broken or external URL.
